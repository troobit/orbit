# Shared JSON Design Critique

Reviewed the completed **18:21Z design merge** against approved requirements, decisions, questions and repository code. Reviewer `codex-gpt-6.1-sol` did not author this revision and differs from its Claude Code/Opus author. No current peer review was read. The concurrently scheduled peer uses this same model, so that pair is fresh-context evidence, not independent-model evidence.

No critical findings. Four major and one minor findings follow.

1. **Major — The extended exec probe can still lose to Kiro's substring heuristic** ([2.1](../../requirements.md#2.1), [5.1](../../requirements.md#5.1), [5.6](../../requirements.md#5.6); detection/Decision 20). Extension occurs only when the initial chunk has no parseable object **and is not Kiro**. In current [detectKiroFormat](../../../../internal/transcript/parser.go), a partial buffer containing `executionId`, `chat` and `metadata` can become Kiro IDE without valid enclosing JSON. A malformed prefix longer than 64 KiB containing those strings, followed by a valid `thread.started`, therefore remains misclassified; discovery's complete-line probe qualifies it. A long first exec object containing those keys has the same boundary problem. **Fix:** settle the same complete-line exec probe before accepting a substring-only Kiro fallback, then preserve the legacy result when probing does not establish exec. Explicitly retain/recombine the unfinished line at the chunk boundary. Add both adversarial prefixes and existing large Kiro fixtures to parity tests.

2. **Major — A valid duplicate rollout does not prove the resolver opens it** ([2.7](../../requirements.md#2.7), [4.2](../../requirements.md#4.2), [5.8](../../requirements.md#5.8); suppression/uniqueness, Decision 17). [findCodexSession](../../../../internal/sessions/resolver.go) stops at the first matching filename before validating its head or readability. The index instead accepts any rollout whose recorded ID matches its filename. If the first duplicate is unreadable/malformed and a later duplicate is valid, that later file can suppress the stream while `codex/<id>` still fails or opens the wrong evidence. Skipping extraction failures in the lister does not change resolver selection. **Fix:** use a shared eligible-candidate rule for all-projects listing, resolution and suppression; index only the candidate actually selected and verified openable. If preserving a legacy resolver choice, keep the stream when that winner is invalid. Test duplicate UUIDs with an invalid first candidate and a valid later candidate.

3. **Major — The Windows cache fallback knowingly misses required changes** ([5.9](../../requirements.md#5.9); cache/Decision 13). The design falls back to size/mtime on Windows and explicitly concedes that an equal-size replacement preserving mtime is missed. Requirement 5.9 requires changed inputs on the next successful refresh; no approved platform exception exists. This can retain stale thread IDs, suppression decisions or project metadata. **Fix:** include platform file identity/change metadata sufficient to detect replacement and ordinary rewrites without transcript-body reads, and test equal-size preserved-mtime replacement through a controllable stat provider. If a platform cannot meet the contract, record that limitation for a requirements decision rather than admitting it as satisfied. No extra reads may quietly defeat the zero-body-read guarantee.

4. **Major — Empty-session metadata has no consistent projection contract** ([1.1](../../requirements.md#1.1), [1.6](../../requirements.md#1.6), [3.1](../../requirements.md#3.1); components 1/3, Decision 19). The table derives a Codex provider from `session_meta`, but the projection says model/provider come only from entries. The sketched metadata adds only `StartedAt`, `Project`, `ThreadID`; a valid header-only rollout has no assistant entry carrying its recorded provider/model. Dispatch before the empty-entry return creates a document but does not preserve these facts. **Fix:** give parsed metadata an explicit first-known summary contract, consistent with chronological entry changes and the per-source table; project recorded header metadata even with zero entries. Test header-only Codex input and later provider changes across file, stdin and ID modes. This need not settle the separate Claude/Kiro scope questions.

5. **Minor — State the detector's classification-to-format mapping** ([2.1](../../requirements.md#2.1), [2.11](../../requirements.md#2.11)). The probe has `exec`, `exec-without-thread` and `other`, but normal detection's return for the second category is unstated. **Fix:** explicitly restrict automatic recognition to the valid initial `thread.started`; threadless exec needs forced conversion, while discovery warns and omits it. Test all three outcomes independently of follow rejection.

Before admission: how will probing bypass a false Kiro heuristic, which exact rollout winner justifies suppression, which Windows fingerprint satisfies refresh guarantees, and where do header-only model/provider summaries live? Preserve unanswered U1–U3 and approved human policies while resolving these technical contracts.
