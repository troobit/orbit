# LM Studio Requirements Peer Review

Reviewed the completed 18:12Z merge's requirements, decisions and questions against current repository code and public authoritative documentation. Fresh-context, non-author review using the same harness/model as the merge coordinator; this is not independent-model evidence. Critiques, other reviews and private logs were not read. No critical findings.

1. **Major — Scope tool links to request occurrences (AC 1.4, 2.3, 3.5, 4.5, 8.3).** A direct file combines different sessions, and complete snapshots repeat historical tool identifiers. The current [Markdown lookup](../../../../internal/transcript/markdown.go), [grouping pass](../../../../internal/transcript/grouping.go) and [HTML lookup](../../../../internal/transcript/html.go) key tool calls/results across the entire transcript by bare ID. Two clients using `call_1` can therefore acquire each other's names, inputs or results; repeated snapshots can also overwrite earlier results. Preserving recorded identifiers does not establish safe internal linkage. **Fix:** require links and rendering groups to respect request/session boundaries, retain original identifiers separately, and test colliding IDs across clients, repeated history and unmatched results in every renderer. Prefix comparison must continue using original recorded identity, so qualification does not defeat history references.

2. **Major — Define admissible request-attribution evidence (AC 2.4, 2.7, 4.1–4.3, 8.4; Decision 3/U4).** “An explicit recorded identifier uniquely links the two” names no supported field, its semantics, or the scope in which uniqueness is checked. A thread ID appearing once in an excerpt is not necessarily a request identifier; another request discovered later can invalidate that inference. Native chat's documented `response_id` identifies a response/context point, and `previous_response_id` continues or branches from that point, rather than identifying the current request ([stateful-chat documentation](https://lmstudio.ai/docs/developer/rest/stateful-chats)). AC 2.7 correctly rejects that shortcut but leaves the positive matching rule undefined. **Fix:** require an evidence-backed list of request-scoped correlation fields and their collision/domain rules before specialised attribution; when none is established for the supported disk grammar, retain unknown attribution. Do not invent correlation syntax solely to make synthetic positive fixtures pass.

3. **Minor — Resolve warning-retention precedence (AC 2.1, 4.2, 4.4; Decision 3/U3).** AC 4.2 retains every unattributed WARN/ERROR body, while 4.4 ignores model-management, startup and engine records without conversation content. A model-management WARN satisfies both. LM Studio's [server-log interface](https://lmstudio.ai/docs/cli/serve/log-stream) covers server operations as well as model IO, so these categories need a deliberate boundary. **Fix:** say whether WARN/ERROR retention overrides routine-category exclusion; test a startup warning and a warning associated with an excluded endpoint. Keep the chosen body/count/reference treatment consistent with U3.

4. **Minor — Explicitly support native chat's string input (AC 2.2–2.3, 8.2).** The translation clause names only “typed `input`” and supplied roles. The [native-chat contract](https://lmstudio.ai/docs/developer/rest/chat) accepts both a plain string and typed text/image items, which do not carry conversation roles. Its plain-string example should not fall through as an unsupported body or lose a role. **Fix:** explicitly translate string input and typed input items as supplied user content, keep `system_prompt` separate, and add both input forms to endpoint fixtures; retain unknown item types generically.

5. **Minor — Specify invalid time-zone configuration (AC 5.1–5.2, 8.3; Decision 4/U8).** The uncertainty policy covers wall times but not an unavailable or invalid `TZ`. Go's [Unix zone initialisation](https://go.dev/src/time/zoneinfo_unix.go) silently falls back to UTC when loading fails; explicit empty `TZ` also means UTC. A misspelled override could therefore produce apparently valid offset-bearing times under an unintended assumption. **Fix:** document accepted zone-setting forms and empty-value semantics, and require a visible diagnostic plus wall-time-only output when a nonempty override cannot be loaded. Test invalid configuration separately from daylight-saving gaps/folds.

Before design admission, resolve the attribution vocabulary and tool-link isolation, then reconcile the three narrower input, filtering and time-zone cases. Existing U1–U8 remain unanswered; this review supplies no human approval.
