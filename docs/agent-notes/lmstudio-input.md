# LM Studio Input Integration (Apsis)

## Current State

- `specs/apsis-lmstudio-logs/` defines the server-log source. All seven phases are implemented: shared representation and time zone, record parser and detection, Markdown/HTML rendering, shared JSON, discovery/identity/cache, session assembly and resolution, and the CLI/`apsis serve` surface.
- The sibling `apsis-shared-json` supplies the common JSON contract and all-projects scope. Its approved requirements remain authoritative; the LM Studio requirements still have unanswered user-owned choices.
- Public LM Studio API documentation defines endpoint payloads, not the disk-log grammar. Earlier structural inspections are labelled as reported observations in the handoff. Fixtures must be synthetic and distinguish those two kinds of evidence.

## Shared Representation (`internal/transcript`)

- `FormatLMStudio`, `Entry.RequestID`/`SuppliedContext`/`Unattributed`/`SourceLine` (all `json:"-"`) and `ParseResult.LMStudioRequests` exist. `LMStudioRequest` lives in `lmstudio_types.go` with the `BodyState*` constants (`not_logged`, `malformed`, `incomplete`, `oversized`; empty = translated).
- `LMStudioRequests` is parallel to `Entries`, not embedded: entries join their request through `Entry.RequestID`. A request with no translatable body has a request row and zero entries.
- `LMStudioRequest.SessionID` is the listed logical-session ID (the request's own ID for a singleton). The parser leaves it empty; the sessions layer must set it with `ID`, since shared JSON's `requests[].session_id` reads it.
- `ParseResult.LMStudioEvents` (`[]LMStudioEventSummary`: root-relative `File`, `NextFile`, per-kind `Counts`, start `Lines`) is filled by session assembly in place of the unattributed entries it drops. Shared JSON projects it as `unattributed_summary`; Markdown and HTML end the session view with it.
- `LMStudioRequest.File` is the record's root-relative file in a session view (shared JSON `requests[].file`, first part of the request meta line) and empty in a direct view.

## Record Parser (`lmstudio_parser.go`, `lmstudio_translate.go`)

- `ParseLMStudioRecords(r, zone)` lexes physical lines: a header `[YYYY-MM-DD HH:MM:SS][LEVEL][tag]... message` starts a record, and everything up to the next header continues it. A header can't occur inside valid pretty-printed JSON, so any header-matching line ends the previous record. Lines that only start like a header (`^\[\d{4}-\d{2}-\d{2}`) get `unparsed_text` warnings when outside a JSON body. Inside a body they make the body malformed.
- Classification order matters (design table): an included `Received request: POST to <path>` first, then the response markers, then any reported POST path (`\bPOST (to )?/...`, which also catches error texts like `(POST /x)`). Only after that does level decide: WARN/WARNING/ERROR are retained, anything else is ignored. An excluded path at WARN is therefore retained as a WARN entry, with its body text as content.
- Body states: no ` with body` gives `not_logged`. A JSON decode failing with EOF/unexpected EOF on the input's last record gives `incomplete` plus an `invalid_record` warning ("body is incomplete at the end of the input", Q47); listings never forward it (Q35), so a growing log adds no listing noise. Any other failure, including an unterminated body followed by another header, gives `malformed` with `invalid_record`. Over `lmMaxRecordBytes` (10 MiB, whole record) gives `oversized`; the bytes are counted but not kept. Text after a complete body is `unparsed_text` and the body is still used.
- Temporary IDs: `LMStudioRequest.ID` and `Entry.RequestID` are `strconv.Itoa(StartLine)`. Request tool IDs are `req:<key>:<recorded>` and response tool IDs `evt:<SourceLine>:<recorded>`; the recorded ID stays on `ItemID`. Native chat `tool_call` output records no ID, so it links by `evt:<line>:output-<index>`. The sessions layer must rewrite `req:` keys before merging files.
- One entry per logged item: each element of `messages`/`input`/`prompt`, a string `input`/`prompt`, and separate `instructions`/`system`/`system_prompt` fields. `PriorPrefixCount` therefore counts entries. Entry types are `user`, `assistant` and `system` (system or developer role). Tool outputs are `user` entries with role `tool`, so the Claude-style result pairing still works. Assistant request entries set `SuppliedContext`.
- `Entry.ItemDigest` is SHA-256 over `field + "\x00" + json.Marshal(decodeJSONValue(item))`. `json.Marshal` sorts map keys, so key order doesn't matter, and `json.Number` keeps number text, so `1.0` and `1` differ. `annotateExtensions` compares digests and resets stale annotations, so it can run again after session assembly.
- `Parameters` is rebuilt from `orderedFields` (shared with `orderedCounters`), with source key order and compact values as logged. Only a string `model` and the endpoint's conversation fields are removed. `client_metadata` stays in, even though thread, parent and kind are read from it: flat `thread_id`, `x-codex-parent-thread-id`, and `request_kind`/`parent_thread_id` inside the `x-codex-turn-metadata` JSON string. Any value containing the truncation marker counts as absent.
- Representation choices for later phases are in decision log Q22–Q27. Log entries use `Type: "log"`, with the WARN/ERROR level in the item's `Status`. Unattributed entries carry `WallTime` because they have no `LMStudioRequest`.

## Discovery, Identity and Cache (`internal/sessions/lmstudio.go`)

- Options: `WithLMStudioLogDir(dir, explicit)`. `""` disables the source (and drops it from `Lister.Sources()`). `explicit` decides whether a missing, non-directory or unreadable root gives `root_unreadable` (Q34). Unlike exec roots, it does not turn on extended ordering (Q38).
- `listLMStudio` returns before touching anything when `projectPath != ""` (7.1). `TestListAll_LMStudioProjectScopeReadsNothing` checks zero opens and zero fingerprints through `ListAll`.
- `findLMStudioFiles` reads two directory levels with `os.ReadDir`: `^\d{4}-\d{2}$` month directories (symlinked ones skipped, because `DirEntry.IsDir` is false for a symlink), then `YYYY-MM-DD.N.log` files. A file symlink is kept as its canonical target when that is a regular file inside the root, keyed by the target's root-relative path, ordered by the earliest name it was found under (Q37). Discovery order is date, numeric suffix, key.
- Identifiers (pure functions, no reads): `lmRequestID(key, startLine)` is `lmstudio-req-p-<base64url(key), no padding>-<line>`, or `lmstudio-req-h-<48 hex of sha256(key)>-<line>` when that would exceed 256 characters. `lmThreadSessionID` is `lmstudio-thread-<48 hex>`. `lmSessionID(req, thread)` is the request's ID for a singleton. `parseLMRequestID` decodes the `-p-` form and accepts only the exact encoding `lmRequestID` produces (round-trip check), so a sign, leading zero or non-canonical base64 is rejected.
- `summarizeLMStudioFile` opens through `lmOpen` (a package variable tests replace to count reads) and runs `transcript.ParseLMStudio`, without the detection probe (1.2). It keeps per request only ID, thread, `Size`, `ResolvedTime` and model. Unattributed-event counts are not cached: session assembly counts them from its own parse (Q39).
- Listing warnings are file-level only (Q35): `path_unreadable`, the parser's `unparsed_text` for a file that yielded no requests and no entries (this is how 7.4's "no recognised records" surfaces; a notice-only file yields nothing *and* no warning), and one `time_zone` per pass. The heuristic exists because the parser emits the same code for "no records found" and "text before the first header".
- Cache: `lmCache{mu, entries}` keyed by canonical path. `lmFingerprint` (package variable) is `statFingerprint`: `golang.org/x/sys/unix.Stat` size, `Mtim`, `Ctim`, inode and device on `unix` builds, and `cacheable == false` elsewhere. A hit requires `cacheable` and an equal fingerprint, so a stub returning identical zero fingerprints still never hits. `buildLMStudioIndex(root, nil)` uses a throwaway cache, so there are no nil checks. The whole pass holds the mutex, and removed files are pruned after it. `NewLister` always creates a cache; a struct-literal `Lister` has none.
- `lmIndex` holds `summaries` (absent = unreadable; also drives cache pruning), `sessions` (ID → `[]lmFileRef` in discovery order) and `order`. Only listing uses it; resolution does not build it (below).
- Rows: `CreatedAt` comes from the first request in discovery order and stays zero when that request has no unique time (5.4). `Model` is the first non-empty one, `Size` the sum of the session's record bytes (`LMStudioRequest.Size`, Q36), with `RequestCount`, `ThreadID` and `Provider: "lmstudio"`. `sourcePriority` is 6.
- `make lint` and CI also run `GOOS=darwin` and `GOOS=windows go vet ./internal/sessions/...` for the build-tagged files.
- Benchmark (`BenchmarkListLMStudio`, 2026-11-10, darwin/arm64 Apple M5 Pro, APFS, warm page cache): 30 files, 5.2 MB, 33,000 requests, 30,010 rows. A cold pass takes about 203 ms and 274 MB allocated; an unchanged refresh about 8 ms and 20 MB with zero body reads (the time goes into regrouping the cached summaries). The unchanged-refresh benchmark fails if any body is read (skipped where the cache is off). `BenchmarkLMStudioListFragment` in `apsisweb` renders `/api/sessions` for the same workload: about 18.2 MB of fragment for 30,010 rows, about 306 ms cold and 126 ms on an unchanged refresh (same machine).

## Session Resolution (`resolveLMStudio` in `internal/sessions/lmstudio.go`, `internal/transcript/lmstudio_session.go`)

- Only all-projects scope with a configured root opens the source; project scope, a disabled source and an identifier of no known shape (`isLMThreadSessionID`, or `lmLocateRequest` failing) return `session not found` before any body read.
- No index is built (Q39). `findLMStudioFiles` gives discovery order from metadata. `lmLocateRequest` matches a request identifier of either form by computing `lmRequestID(f.key, line)` for each discovered file, so `-h-` IDs open one file like `-p-` IDs, and a crafted `../` key never matches. A thread ID parses every discovered file once and keeps the files that hold it. `parseLMRequestID` is now only exercised by tests (it checks the `-p-` form's reversibility).
- `readLMStudioFile` opens through `lmOpen`, rechecks that the canonical path is unchanged and inside the root, parses with `ParseLMStudio`, then calls `transcript.AssignLMStudioIDs`. That rewrite must happen per file before merging, since temporary keys (`StartLine`) repeat across files. It rewrites `ID`/`SessionID`, entry `RequestID`, and the `req:<key>:` prefix of `ContentItem.ID`/`ToolUseID`; `evt:` IDs and `ItemID` are untouched.
- `transcript.AssembleLMStudioSession(parts, keep)` keeps requests whose `ID` or `SessionID` equals the opened identifier (so a threaded request's own ID opens just that request), sets `File`, keeps only their entries, re-runs `annotateExtensions` over the merged order (so prefixes compare across files), builds one `LMStudioEventSummary` per contributing file via `CountLMStudioEvents`, keeps only warnings whose line falls inside a selected request (message prefixed with the file) plus one `time_zone`, and sets `Metadata.ThreadID` from the first request (Q40, Q42).
- An unreadable file of a thread becomes a `path_unreadable` parse warning; when the opened identifier names a request, its file being unreadable is an error.
- The result rides on `SessionMetadata.PreParsed`; `Reader` is an empty `NopCloser`, `Path` is empty, `Size` is the selected records' bytes (the web size guard reads it), `CreatedAt` is the first request's time or zero. `ParseResolved` returns `PreParsed` first. `ResolvePath(SourceLMStudio)` always errors, so Phase 7 must reject `-F` by source, not by a failed `ResolvePath`.

## CLI and `apsis serve` (`cmd/apsis/main.go`, `internal/apsisweb/`)

- `lmStudioLogDir(*string)`: the flag (nil when absent) replaces `APSIS_LMSTUDIO_LOG_DIR`, read with `os.LookupEnv`, so `APSIS_LMSTUDIO_LOG_DIR=` disables the source. With neither set, the directory is `~/.lmstudio/server-logs` and `explicit` is false (Q34). `flagValue(fs, name)` uses `FlagSet.Visit` to tell an empty flag from an absent one.
- Direct conversion: `convert` calls `lmStudioInput` → `sessions.AssignLMStudioInputIDs(res, in.path, in.lmStudioLogDir)` for every LM Studio result except an assembled session (`PreParsed`). A file gets listed identifiers only when `findLMStudioFiles` lists it (matched by canonical path, so a symlink takes its target's key). Other files are keyed by their canonical absolute path and stdin by `stdin`; those are input-scoped and documented only in help (Q43). The document's own `session.id` stays empty for a `.log` file.
- Rejections (Q45): `errFollowLMStudio` comes from `validateFollowMode` (`-a lmstudio`), `resolveFollowInput` (`-s lmstudio`, a detected file through `followFileError`, or a bare ID that `Resolve` finds) and `runLatest`. `errRawJSONLMStudio` comes from `convert` (resolved source or `-a`; a resolved session's reader is empty, so `convertToJSON` would otherwise print "no data") and from `convertToJSON` after detection. `latestLMStudioError` wraps either one, so tests use `require.ErrorIs`.
- `lmstudio` is last in `resolveInput`'s bare-ID list. A bare thread-shaped ID reads every log body before it reports not found, but only in all-projects scope.
- `apsisweb.New` passes the directory on only with `AllProjects`, so project scope has no `lmstudio` pill. `Config.NetworkWarning()` adds the disclosure when `Bind == "0.0.0.0"` and the source is listed. The transcript view shows warnings and the thread ID for `lmstudio` as for `codex-exec`. `cliCommand` gives the oversized-session instruction `apsis --all-projects -s lmstudio <id>`.
- `SessionInfo.SizeLabel()` (`N requests` for LM Studio, `FormatSize` otherwise) feeds both `apsis -l` and the web list. A zero LM Studio time prints `time unknown` in `apsis -l`; the web list shows `time unknown` for any zero time.

## Detection (`parser.go`)

- `DetectFormat` runs `probeLMStudio` after Kiro's validated check and before the exec probe, so a matched log never reaches the exec probe, which would otherwise read the whole file. If the chunk has headers but no included request, the substring Kiro guess is skipped and `errLMStudioWithoutRequest` is returned. `Parse` checks for that error and returns it instead of falling back to the Claude parser.
- Auto-detected and `-a lmstudio` input both render through the LM Studio renderer (below).

## Rendering (`lmstudio_render.go`)

- `RenderOptions.LMStudio` (a `*LMStudioView` from `NewLMStudioView(res)`, nil for every other format) switches `RenderMarkdown` and `renderEntriesToBuilder` (standalone and fragment HTML) to the LM Studio body. The CLI and `apsisweb.handleTranscript` set it unconditionally. The CLI's "no entries" check also accepts a result that only has requests, since a body-less request still renders its boundary.
- `segments` interleaves `Requests` and log-level entries (`RequestID == ""`) by start line. That only works in a direct view of one input; a session view has no log-level entries, so its requests keep their merged order. `LMStudioView.Events` (from `LMStudioEvents`) renders after the requests as "Unattributed events in these log files", one `eventSummaryParts` line per file, after a notice naming `apsis -a lmstudio <file>` (Q41). `lmInlineCodeHTML` turns that notice's backquoted spans into `<code>` so both formats show the same command.
- Both formats build every label from the same helpers (`requestParts`, `eventParts`, `notes`, `lmParameterSummary`, `lmPrefixText`, `lmBodyStateLabels`), so parity comes from sharing them. `lmPartsMarkdown` and `lmPartsHTML` only differ in how recorded values are quoted.
- Tool pairs render at the call, not the result (Q28): `formatToolUse`/`formatToolUseHTML` defer generic tools, and the LM Studio renderer then writes the combined block immediately and marks the call `paired`, so the result site skips it. HTML uses `toolResultBlockHTML`, the section-free part of `formatToolResultHTML`; the wrapped form would open a new Assistant section and detach the call from its "supplied context" heading. `BuildToolMeta` is prebuilt over all entries so a result whose call sits in a repeated prefix still finds it.
- Tool-result-only entries get no heading. Assistant text and thinking go through `markdownToHTML` in HTML; user, system and tool text is escaped in `<p>`, as in the existing renderers.
- `lmMarkdownSource` backslash-escapes `<Truncated in logs>` in text read as Markdown. Parameter JSON and log text are in code blocks and stay as logged.
- Goldens are `testdata/lmstudio/{threads,tools,classification,recovery}.{md,html,fragment.html}.golden`; regenerate with `go test ./internal/transcript -run TestLMStudioRender_Goldens -update`. The parity test checks boundary order, shown text and marker counts across Markdown and fragment HTML, and that standalone HTML contains the fragment.

## Time Zone (`lmstudio_timezone.go`)

- `zoneFromEnvironment()` reads `TZ` with `os.LookupEnv` and calls `resolveZone(tz, set)`: unset → `time.Local` (label `host local zone`), empty → UTC, otherwise an optional leading `:` then an absolute path (`filepath.IsAbs`, so drive/UNC on Windows) via `os.ReadFile` + `time.LoadLocationFromTZData`, or an IANA name via `time.LoadLocation`. Failure gives `loc == nil` plus a warning; nothing substitutes another zone.
- `:` alone and `Local` are rejected explicitly, because `time.LoadLocation` silently maps `""` to UTC and `"Local"` to the host zone.
- `zoneResult.interpret(wall)` returns an offset-bearing instant only when the wall time maps to exactly one instant. It tries the offsets in force 24 hours either side of and at the wall time; nonexistent (gap) and ambiguous (repeated hour) times, invalid dates and a failed zone all return false.
- The package blank-imports `time/tzdata` (about 450 KB in every binary that links `transcript`, including `orbit`). The embedded data is only a fallback: Go consults `ZONEINFO` and the system zone directories first. The no-system-database path cannot be tested in-process because those directories cannot be disabled; `go list -deps ./cmd/apsis` shows the import is linked.
- Tests build a fixed-offset version-1 TZif file in-process (`fixedTZif`), so the path form is tested without platform zone files.

## Current Integration Points

- `transcript.DetectFormat` reads at most 65,536 bytes and returns the consumed prefix for replay. Detection and full record parsing are separate concerns; a startup-heavy log can require forced parsing.
- CLI raw JSON uses `convertToJSON`, which bypasses normalized transcript rendering. It treats non-Kiro input as JSONL, so a future LM Studio rejection must cover that path separately.
- Follow mode resolves through `resolveFollowInput` or `runLatest` before starting the Claude-shaped follower. Checking only the normal conversion path cannot reject every unsupported source/mode combination.
- Source registration spans `AllSources`, `IsValidSource`, CLI resolution order, the lister and resolver. A listed logical LM Studio session can span files and select only part of each; opening one backing file is insufficient.
- `apsisweb.handleTranscript` currently parses a resolved reader and renders entries without passing parse warnings into its view data. The LM Studio proposal requires visible warnings in this path.
- The web transcript size guard uses `resolved.Metadata.Size`. The LM Studio proposal counts selected session-owned records, rather than every byte in files shared with other sessions.
- Request snapshots can repeat source tool IDs. Existing renderers match IDs across the whole transcript; see [Transcript Metadata Flow](transcript-metadata.md). A future LM Studio design must preserve request-local linking and original source IDs separately.
- No request-scoped correlation field is established for the proposed disk grammar. The requirements keep all response/diagnostic attribution unknown; a unique thread or response ID in an excerpt is insufficient evidence of request ownership.

## Policy Boundaries

- A direct file/stdin view and a listed logical-session view have different scopes. Keep source order, logical membership and unknown attribution explicit rather than treating a containing file as one conversation.
- Direct log evidence is inspected through CLI conversion. Proposed browser session pages show body-free references and CLI instructions, with no new file-serving or upload route.
- Proposed request parameters remain logged evidence outside conversation messages; selective credential redaction is not implied. Discovery help and its unanswered opt-in choice disclose those values alongside prompts.
- Enabled LM Studio discovery participates in the sibling's inclusive all-projects `latest`; the independent review's source-filter workaround was rejected because it changes that contract. Singleton volume and unsupported follow/raw-JSON outcomes remain explicit policy consequences.
- Client prompt text is not authoritative project metadata. Correlation identifiers do not by themselves establish project ownership or request-response attribution.
- Headless review can resolve routine technical gaps and record local admission; it cannot manufacture approval for unanswered discovery, grouping, attribution or presentation choices.
